# 查询数据与资源选择：Pose History、Trajectory、Chooser、Proxy Table

> Motion Matching 和数据驱动动画选择是否稳定，取决于系统能否描述“刚才怎样动、接下来想怎样动，以及当前允许用哪些资源”。

## Pose History：保存跨帧的姿势证据

Pose History 保存一段过去时间内的骨骼姿势采样，供 Pose Search 查询当前姿势与候选动画能否自然接续。它保存的是跨帧数据；Cached Pose 只是在当前帧复用已计算的 Pose，二者不能互换。

历史长度、采样骨骼和更新时间会影响查询质量与成本。历史过短时，系统难以区分刚起步、刚转向或已稳定循环的相近姿势；采样过多则增加计算和数据库特征维度。

## Trajectory：把移动意图变成可比较的曲线

Trajectory 同时描述角色过去的移动，以及根据输入、朝向和移动模型预测的未来位置、朝向和速度。Pose Search 的 Trajectory Channel 会在若干采样点上比较这些特征，以选择运动趋势相近的动画姿势。

它不是最终 Pose 节点，也不会修复错误的移动预测。输入方向频繁跳变、加速度模型和实际移动不同步时，检索会不断改变候选姿势；应先验证轨迹可视化，再怀疑数据库质量。

## Chooser：先限制候选资源

Chooser 根据上下文对象、Gameplay Tag 或状态字段，从表格规则中返回合适的动画、Montage、Pose Search Database 或其他对象。它的职责是回答“现在允许使用什么”，不是混合两个 Pose。

例如可先按移动模式、姿态、步态和武器状态筛掉不应参与检索的数据库，再交给 Motion Matching 查询。这能把散落的 `if / switch` 选择逻辑收拢成可检查的规则，但规则的输入字段必须和游戏状态在同一更新节奏上。

## Proxy Table：延迟解析具体资产

Proxy Table 用一个间接引用表示资源，再按上下文解析为某个具体对象。它适合按体型、武器、角色风格或平台替换资产，而不让每个调用点都硬引用最终动画。与 Chooser 相比，它更偏“映射到哪个实现”；两者可组合使用，也都不直接修改姿势。

## 与 Motion Matching 的关系

```text
角色状态 / 输入 ─→ Trajectory ─┐
当前动画姿势 ─→ Pose History ──┼─→ Pose Search 查询
玩法上下文 ─────→ Chooser ──────┘      │
                                      候选姿势
```

Motion Matching 的 Schema、Database 和采样成本见 [MotionMatching 专题](../MotionMatching/README.md)。这里的四个模块只负责提供查询数据或缩小候选集合，不能替代姿势检索本身。
