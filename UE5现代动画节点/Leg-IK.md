# Leg IK 详解

> Leg IK 做的事一句话就能说清：给定一个「脚该到的目标」，它只负责把大腿—小腿—脚这段骨头重新解算一遍，让脚真正够到那个点。它的边界同样清楚——它不决定脚该踩哪儿，也不替你挪骨盆；它只回答一个问题：「这段腿，怎么摆才能让脚到那儿」。

## 它解决的问题

上游（Foot Placement、Orientation Warping、手工曲线）算出了一个「脚的目标变换」——脚应该落在哪、朝哪个方向。但这个目标通常只写在一根 IK 脚参考骨上，动画里的大腿、小腿、脚还是按 FK 姿势摆着，两者对不上。目标脚在前方 40cm，实际 FK 脚却还停在原地，腿就悬空或陷地。

Leg IK 就是来补这「最后一公里」的：它读入脚的目标变换，把 hip→knee→foot 这段腿链重新解算，让脚落到目标上。

它明确**不做**三件事，理解了边界才不会误用：

- **不决定「脚该踩哪里」**：目标从哪来它不管，只消费上游给的目标。它是纯执行者。
- **不挪骨盆、不补高度**：髋（链根）的位置保持不动。目标太远够不到，它就伸直腿停在最大可达处，不会把腿拉长，也不会把骨盆往下拽。
- **不改骨骼长度**：解算用的每一段长度都取自当前 FK 姿势，全程固定。

## 核心思想：把「够到」拆成三步

`FAnimNode_LegIK` 是一个骨骼控制节点（Skeletal Control），在**组件空间**里改骨头：父类 `FAnimNode_SkeletalControlBase` 负责给它喂 `ComponentPose` 输入、Alpha 混合和 LOD 门槛，它自己只负责算出「该改哪些骨、改成什么样」。每帧对每条腿依次做三件事：

1. **对齐方向（Orient）**：把整条腿当成刚体，绕髋转一下，让「髋→脚」的方向指向目标。这一步只改朝向、不改长度。
2. **够到目标（Reach）**：保持各段长度不变，重新摆 hip-knee-foot（或更长链），让脚真正落在目标上。这是求解的主体。
3. **膝盖扭转校正（Twist）**：绕「髋→脚」这根轴再转一下，让膝盖平面和脚的前向对齐，把脚的朝向也落实。

最后用 IK 目标的旋转覆盖 FK 脚的旋转，再把这段腿的改动一次性写回姿势。

其中第 2 步有两条路：腿链正好是三块骨（脚、膝、髋，两个骨节）时用**两骨闭式解**，一次算完；链更长（脚上带趾骨、或自定义多节腿）时退回 **FABRIK** 迭代。所以节点才要 `NumBonesInLimb` 这种配置——告诉它从脚往上数几级骨算作「这条腿」。

### 膝盖往哪弯：弯曲方向是从动画里「抄」出来的

两骨 IK 有一个先天二义性：髋和脚的位置定了、两段长度定了，膝盖仍可以在「髋-脚连线」的两侧各有一个解。Leg IK 没有让你填一个 pole vector，而是**从当前 FK 姿势里提取**膝盖现在弯向哪边，用那个方向当弯曲方向去解。

这个设计的妙处在于：动画师在动画里摆的膝盖朝向会被原样继承，而不是被一个写死的极向量顶掉。但「从动画里提取」有个脆弱点——当腿几乎完全伸直时，「弯向哪边」在数值上变得不确定，膝盖可能在某一帧突然翻到另一侧。

所以节点提供了 `HingeRotationAxis`（髋-膝-脚所在平面的法线）：解算时一旦发现膝盖弯得够明显，就把当前的弯曲方向缓存下来；腿太直时，用缓存的方向配合这条轴把弯曲方向重建出来。相当于「平时抄动画、腿伸直时用记忆兜底」，而不是靠一个固定极向量。没设这条轴，腿一伸直就没有兜底，膝盖就会乱翻。

## 局部腿链怎么解：固定长度 + 余弦定理

对标准的「脚-膝-髋」三块骨，问题归结为：已知髋位置、脚目标、两段长度（髋-膝、膝-脚），求膝盖位置。解法是余弦定理——把髋到脚的距离当底边、两段长度当腰，膝盖就是三角形的顶点，落在哪一侧由上面说的弯曲方向决定：

```text
膝盖位置 = 髋 + 腿长 · ( 髋→脚方向 · cos θ + 弯曲方向 · sin θ )
```

`θ` 由三边长度用余弦定理求出。整个过程只有位置运算，长度始终不变——「够到」本质上是把髋、膝、脚三块骨原有的旋转**重新分配**，让脚达到目标，而不是缩放任何一段。

超过三块骨的链，三边关系不成立了，就退回通用的 FABRIK 迭代：一遍「从末端往前够」、一遍「从根往后收」，反复交替，直到脚和目标之间的距离（slop）小于阈值、或到达迭代上限、或发现不再收敛就停。

### 目标不可达：为什么不无条件拉长腿

这是理解 Leg IK 边界最关键的一点。求解前它先做一次判断：**目标到髋的距离是否小于整条链的总长**。

- 够得着 → 正常解算。
- 够不着、且没开 Soft IK → 不做任何求解，直接把各段骨头沿「髋→目标」方向**打直**，脚停在最大可达距离上。注意是「打直」，不是「拉长」——每一段长度仍是原始的，脚离目标还差一截，就差在那里。

也就是说，当目标超出腿长，Leg IK 的选择是「伸到极限、保持长度、接受够不到」，而不是把腿拉变形去硬凑。这个残差必须由上游负责：要么 Foot Placement 给出更近的落点，要么 Pelvis IK 把骨盆降下来缩短距离。**骨盆高度和目标距离是上游的责任，Leg IK 不越权。**

### Soft IK：给「完全伸直」留一点缓冲

腿在接近完全伸直时，膝盖侧向的弯曲方向会突然失去意义，视觉上就是膝盖「啪」地一下绷直（pop）。Soft IK 就是为此准备的：它把「软」的区间定义成链长的某个百分比（`SoftPercentLength`），当目标距离超过这个百分比后，不再线性逼近，而是让脚以越来越小的增量逼近完全伸直，膝盖平滑地「慢慢打直」，而不是瞬间绷紧。

这也解释了为什么 Soft IK 和「不可达判断」会纠缠在一起：开了 Soft IK 后，即使目标超出总长，也不再走「直接打直」那条短路，而是进入正常解算，让软化后的目标把腿带向极限。

## 它不碰什么、和谁配合

Leg IK 是整条下半身修正链路里的**执行层**，放对位置才有效：

- **Foot Placement 是「规划层」**：回答「脚该踩哪里」。它预测落点、判断能不能踩，把脚的目标（位置和朝向）写进 IK 脚骨，不做解算。
- **Orientation Warping 是「方向修正层」**：把 IK 脚的目标随移动方向掰过去（改目标位置/朝向），让下肢对齐真实移动，也不解算腿链。
- **Leg IK 是「执行层」**：消费上面两者写好的目标，把大腿—小腿—脚真实地解算过去。

所以在官方 Game Animation Sample 的 Blend Stack 里，顺序通常是 **Foot Placement → Orientation Warping → Leg IK**：先规划、再掰方向、最后执行。执行永远在最末，因为它是唯一真正改大腿/小腿/脚骨头的一方；把它放前面，后面的节点又会把它解好的姿势覆盖掉。

## 常见问题

- **节点「没反应」**：优先查配置，不是查引脚。每条腿必须能从脚往上数出至少三块骨（脚、膝、髋），数不够的腿会被静默跳过；`IKFootBone`（通常是虚拟骨）和 `FKFootBone`（真实脚骨）缺一个也会失效。
- **膝盖突然翻到另一侧 / 绷直时乱跳**：先确认 `HingeRotationAxis` 设对了（髋-膝-脚平面的法线）。没设它，腿太直时弯曲方向没有缓存兜底，就会翻面。
- **脚快伸直时膝盖「啪」地绷一下**：这是典型的完全伸直 pop。把 `SoftPercentLength` 调到略小于 1（比如 0.97）并打开 `SoftAlpha`。
- **脚永远够不到、悬在目标外**：这不是 Leg IK 坏了，是目标太远。Leg IK 只在腿长内求解；要么把骨盆降下来（Pelvis IK），要么让 Foot Placement 给更近的落点。
- **脚的方向没跟上**：膝盖扭转校正需要 `FootBoneForwardAxis` 指对脚的「前」，并且打开 `bEnableKneeTwistCorrection`；想注入主动的膝盖扭动，走 `TwistOffsetCurveName` 曲线。
