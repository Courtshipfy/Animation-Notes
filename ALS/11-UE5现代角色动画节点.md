# 11 UE5 现代角色动画节点

> UE5 的现代角色动画方案不再只依靠状态机和 Blend Space 选择完整动画，而是先选择接近目标的姿势，再使用 Warping、IK、根骨补偿和动态过渡对姿势进行运行时修正。

## 为什么会出现这些新工具

传统移动动画系统通常需要手工完成大量工作：

- 按速度和方向选择 Walk、Run、Sprint 动画；
- 制作足够多的前后左右与转向资产；
- 用播放速率和步幅曲线减少脚滑；
- 自己实现 Foot Trace、Foot Lock 和 Pelvis Offset；
- 为起步、停止、Pivot、落地编写专门状态和过渡规则。

UE5 的新工具并不是用一个节点替换整个系统，而是把这些问题拆成更通用的运行时模块：

```text
玩法意图与角色运动
        │
        ├─ Motion Trajectory：预测角色准备怎样移动
        │
        ├─ Chooser：根据玩法上下文选择候选动画数据
        │
        ├─ Motion Matching：从数据库选择合适的动画姿势
        │
        ├─ Blend Stack / Dead Blending：平滑切换姿势
        │
        ├─ Orientation / Stride Warping：修正方向和步幅
        │
        ├─ Offset Root Bone / Motion Warping：修正根骨与目标位置
        │
        └─ Foot Placement / Leg IK / FBIK：处理脚部接触和全身约束
```

项目不一定要使用整条链路。传统状态机也可以只引入其中一两个节点，例如先用 Stride Warping 改善脚滑，或者用 Distance Matching 改造停止动画。

## 先区分“节点”和“系统”

这些功能经常被统称为“新动画节点”，但它们在引擎中的形态并不相同。

| 功能 | 主要形态 | 解决的问题 |
| --- | --- | --- |
| Foot Placement | AnimGraph Skeletal Control | 脚部接触、地面适配和骨盆补偿 |
| Orientation / Stride / Slope Warping | AnimGraph 节点 | 方向、步幅和坡面姿势修正 |
| Leg IK | AnimGraph Skeletal Control | 把单条腿解算到已有脚部目标 |
| Full Body IK | Control Rig Graph 节点 | 多个末端目标共同影响全身 |
| Offset Root Bone | AnimGraph 节点 | 允许根骨相对胶囊偏移并受控回收 |
| Motion Matching | AnimGraph 节点 + Pose Search 资产 | 从数据库动态选择姿势 |
| Pose History | AnimGraph 节点 | 保存历史姿势并向 Pose Search 提供查询数据 |
| Blend Stack | AnimGraph 节点/内部混合图 | 管理连续的动态姿势切换 |
| Inertialization / Dead Blending | AnimGraph 过渡节点 | 使用运动趋势平滑姿势切换 |
| Distance Matching | Library / Node Function + Sequence Evaluator | 按距离而不是时间推进动画 |
| Motion Warping | Component + Montage Notify State + 蓝图函数 | 把 Root Motion 对齐到场景目标 |
| Motion Trajectory | Component / 查询数据 | 描述角色过去和未来的运动轨迹 |
| Chooser / Proxy Table | 选择资产和数据框架 | 根据上下文筛选动画、数据库或其他对象 |

因此，找不到某个“AnimGraph 节点”不一定是插件没有启用，也可能是它本来就属于角色组件、Control Rig、动画节点函数或资产选择系统。

## 接触与 IK

### Foot Placement

Foot Placement 是 Animation Warping Runtime 中的高级脚部放置节点。它面向的不是单纯“两条射线加 Two Bone IK”，而是一套脚部接触求解：根据腿部定义、脚部接触状态、地面信息和角色运动，计算脚掌目标、骨盆调整以及脚从支撑到摆动的过渡。

它适合解决：

- 双脚在斜坡和台阶上的高度差；
- 脚掌朝向与地面法线不一致；
- 调整脚部后腿长不足，需要同步移动骨盆；
- 支撑脚在角色胶囊移动时需要保持稳定；
- 从站立到移动、从支撑到抬脚时需要平滑释放。

Foot Placement 不等于 Foot Lock，也不等于 Foot Trace：

- Foot Trace 只负责发现地面位置和法线；
- Foot Lock 只负责保存并维持支撑脚锚点；
- Foot Placement 是更高层的求解器，可以在同一流程中使用地面、腿部和脚掌状态完成放置与稳定。

这意味着它有能力取代传统方案中的一部分 Foot Offset、Pelvis Offset 和 Foot Lock 工作，但不能直接把旧系统的输入变量原样接过去。骨骼轴向、腿部定义、接触曲线、角色运动状态和节点执行顺序都需要重新配置。

在 ALS 中，[脚部 IK 锁定](./08.1-脚部IK锁定.md) 主要在 C++ 中保存世界空间锁点，再把最终目标交给 Control Rig。迁移到 Foot Placement 时，应先决定是否由新节点统一负责脚部稳定；如果旧 Foot Lock 和 Foot Placement 同时修改同一只脚，容易出现双重补偿、脚掌吸附或骨盆抖动。

Foot Placement 的具体属性和成熟度在 UE5 小版本之间变化较明显。使用前应以当前项目版本的 `FAnimNode_FootPlacement` 属性和 Animation Warping 插件状态为准。

### Leg IK

Leg IK 是更基础的 AnimGraph Skeletal Control。它接收已经确定的脚部 IK 目标，解算大腿、小腿和脚骨，使脚到达目标位置。

它不负责：

- 检测地面；
- 判断脚什么时候应当锁定；
- 选择动画；
- 自动决定骨盆应该移动多少。

因此可以把它理解成执行层：上游系统决定脚要去哪里，Leg IK 负责让腿到达那里。Game Animation Sample 也使用 Leg IK 把脚固定到经过 Pose Warping 修正后的 IK Foot Bone 位置。

### Full Body IK

Full Body IK（FBIK）是 Control Rig Graph 中的全身求解节点，来自 FullBodyIK 插件。它可以同时处理脚、手、头部等多个 Effector，并通过每根骨骼的 Stiffness、Preferred Angle 和 Rotation Limit 控制整条身体链如何响应。

与 Leg IK 相比：

- Leg IK 主要解决一条腿到达脚部目标；
- FBIK 会让多个末端目标共同影响骨盆、脊柱和四肢；
- FBIK 更适合攀爬、双手持物、全身地面适配和复杂交互；
- FBIK 的配置与运行成本也更高，需要控制不必要的骨骼和 Effector。

FBIK 本身位于 Control Rig Graph。动画蓝图通常通过 Control Rig 节点执行包含 FBIK 的 Rig，而不是直接在 AnimGraph 中搜索一个完全等价的普通 Skeletal Control。

## 运动方向与步幅适配

### Orientation Warping

Orientation Warping 修改腿部 IK 骨骼的运动方向，并将部分旋转分配到脊柱，使一个基础移动动画覆盖更多实际移动方向。

例如动画原本向前跑，但角色实际速度相对身体偏右 `35°`，节点可以把腿部运动方向转向右侧，同时通过脊柱扭转尽量维持角色面向。它解决的是“动画运动方向”和“实际移动方向”不一致，而不是让 Actor 本身旋转。

这与 ALS 的 `MovementDirection` 和 `RotationYawOffsets` 有部分重叠：

- ALS 通过方向分类、方向动画和曲线偏移组织表现；
- Orientation Warping 直接对当前姿势做运行时方向变形；
- 动画覆盖不足时，Warping 可以减少需要制作的中间方向资产；
- 大角度变形仍可能破坏步态，不能用一条前进动画无限覆盖所有方向。

### Stride Warping

Stride Warping 根据角色实际移动速度和动画 Root Motion 速度调整双脚之间的步幅。官方给出的核心关系可以概括为：

```text
StrideScale = LocomotionSpeed / RootMotionSpeed
```

角色比动画标定速度快时，节点扩大步幅；角色更慢时，缩短步幅。这样可以减少只靠提高播放速率导致的碎步，也可以降低为每个速度制作独立动画的需求。

它与 ALS 的 Stride Blend 目标相似，但实现方式不同：

- ALS 使用速度曲线产生 `StrideBlendAmount`，再配合 Play Rate；
- Stride Warping 直接修改脚部姿势中的跨步距离；
- 两者同时启用时必须重新标定，否则可能重复扩大或缩小步幅。

播放速率仍然有价值。Stride Warping 主要调整空间距离，Play Rate 主要调整时间节奏；合理系统通常在有限范围内同时控制二者。

### Slope Warping

Slope Warping 根据坡面方向修改下半身姿势，使脚步和腿部运动更符合上坡或下坡。它处理的是整个移动姿势相对坡面的变化，而不仅是把最终脚掌旋转到地面法线。

它可以和 Foot Placement 配合：

- Slope Warping 先让移动周期整体适应坡度；
- Foot Placement 再处理每只脚的实际接触点和骨盆高度。

如果只使用脚部 IK 而不调整整体姿势，在陡坡上容易出现膝盖抬升不足、腿部压缩过大或身体仍保持平地跑姿的问题。

### Steering

Steering 用于在动画播放过程中逐渐引导根运动方向，使选中的动画更接近目标轨迹。Game Animation Sample 将 Steering 放在 Motion Matching 节点的 Blend Stack Graph 内，与 Orientation Warping 一起修正匹配后的动画。

它比单纯扭转腿部更接近“调整动画运动轨迹”。该功能在不同 UE5 版本中的节点接口和示例结构可能变化，使用时应以目标版本的 Game Animation Sample 为准。

## 距离和根运动适配

### Distance Matching

Distance Matching 让动画按照“距离”而不是固定时间推进。动画资产需要一条 Distance Curve，运行时根据当前距离查找对应姿势，并通常通过 Sequence Evaluator 和 Animation Node Function 更新显式时间。

典型场景包括：

- 停止动画：根据剩余制动距离选择脚步阶段；
- Pivot：根据到转向点的距离推进动画；
- 落地：根据角色到地面的距离选择落地准备姿势；
- 起步：根据已经移动的距离控制蹬地阶段。

它不是一个把输入 Pose 接到输出 Pose 的普通修正节点。核心能力来自 Animation Locomotion Library、动画距离曲线和节点函数。官方流程也特别要求可运行时索引的曲线压缩设置。

与 ALS 的固定 Start/Stop 状态相比，Distance Matching 可以让同一停止动画适配不同进入速度和制动距离，但前提是距离预测、动画曲线和移动模型彼此一致。

### Motion Warping

Motion Warping 动态修改 Montage 的 Root Motion，使动画在指定窗口结束时到达一个场景目标，例如翻越点、处决位置、开门位置或攀爬边缘。

它由三部分组成：

1. Montage 中的 Motion Warping Notify State 定义允许修正的时间窗口；
2. 角色上的 Motion Warping Component 管理 Warp Target；
3. 蓝图或 C++ 在播放动画前设置目标位置和旋转。

所以 Motion Warping 不是 AnimGraph 姿势节点。它修改的是 Root Motion 轨迹，并且只在指定动画窗口内生效。普通连续移动、脚部地面贴合和方向 Blend 不应全部交给它处理。

### Offset Root Bone

Offset Root Bone 允许动画根骨在一定范围内相对角色胶囊产生位置和旋转偏移，然后按规则释放或回收到胶囊中心。

它适合解决胶囊驱动移动与动画 Root Motion 细节之间的矛盾：

- 起步和 Pivot 时，Mesh 可以暂时保留动画中的位移惯性；
- Root Bone 可以独立旋转，表现更自然的转身和方向变化；
- 停止后再把偏移逐渐释放，避免角色空闲时 Mesh 长期偏离胶囊。

这和 Motion Warping 不同：Motion Warping 把根运动对齐到外部目标；Offset Root Bone 管理 Mesh Root 与胶囊之间的内部偏差。

Game Animation Sample 将 Offset Root Bone 标记为实验性功能，并记录了缺少碰撞检查、与 Montage Motion Warping 叠加可能产生额外移动等限制。因此它很适合研究现代运动方案，但上线前需要针对所用 UE 版本重新验证。

## 姿势选择、轨迹与过渡

### Motion Matching 与 Pose Search

Motion Matching 是 Pose Search 插件中的 AnimGraph 节点。它不先决定“进入 Run 状态”，而是使用 Pose Search Schema 定义的查询特征，在一个或多个 Pose Search Database 中寻找当前最合适的动画姿势。

查询通常包含：

- 角色过去和未来的运动轨迹；
- 脚部等关键骨骼的位置和速度；
- 当前姿势与候选姿势的连续性；
- Gameplay Tag、数据库过滤和附加代价。

它可以替代一部分大型移动状态机和方向 Blend Space，但并不自动解决脚部接触、地面适配和所有过渡问题。官方 Game Animation Sample 仍然把 Orientation Warping、Steering、Offset Root Bone、Leg IK 和 Dead Blending 叠加在 Motion Matching 结果之后。

本仓库已经将 Motion Matching 单独放在 [`MotionMatching/`](../MotionMatching/) 中，本篇只记录它和其他现代节点的组合关系。

### Pose History

Pose History 保存过去一段时间的角色姿势和骨骼采样，并可引用或生成运动轨迹。Motion Matching 使用这些历史数据构造当前查询，判断候选姿势是否能自然接续当前动作。

它不是动画缓存姿势节点的简单替代：Cached Pose 用于避免重复计算一张姿势；Pose History 用于保存跨帧数据，供 Pose Search 比较历史与轨迹。

### Motion Trajectory

Motion Trajectory 描述角色已经怎样移动，以及根据输入和移动模型预计将怎样移动。Motion Matching 的 Trajectory Channel 会在这些轨迹采样点上比较位置、方向和速度。

它通常以组件或轨迹数据的形式存在，不是最终输出 Pose 的节点。轨迹预测质量会直接影响 Motion Matching：如果移动组件预测的未来方向经常突变，数据库再完整也会频繁选择不稳定的动画。

### Chooser 与 Proxy Table

Chooser 是上下文驱动的对象选择框架。Game Animation Sample 使用 Chooser 根据步态、姿态、移动模式和玩法状态筛选 Motion Matching 可以查询的 Pose Search Database，也可以选择 Montage、动画或其他对象。

它不是姿势混合节点，而是回答“当前允许使用哪些资源”。这样可以把大量 `if / switch` 和资产硬引用移到表格化规则中。

Proxy Table 提供更间接的资源映射：系统先引用一个 Proxy，再根据上下文解析成具体资产。它适合角色体型、武器、动画风格或平台差异较大的项目。Chooser 和 Proxy Table 的接口仍在持续发展，应根据目标 UE5 版本决定是否作为项目核心依赖。

### Blend Stack

Blend Stack 用于管理连续进入的动态动画姿势，并为每次选择建立混合记录。它特别适合 Motion Matching 这种可能随时切换到数据库中任意姿势的系统。

Game Animation Sample 还在 Motion Matching 节点内部的 Blend Stack Graph 中执行 Orientation Warping 和 Steering，使这些修正作用于每次被选中的动画。它不仅是传统 `Blend Poses` 节点的另一种写法，而是面向动态姿势流的混合基础设施。

### Inertialization 与 Dead Blending

Inertialization 不要求同时持续计算来源姿势和目标姿势，而是记录切换瞬间骨骼的变化趋势，再让这些偏差逐渐衰减到新姿势。它能降低复杂状态切换的混合成本，也适合短时间内频繁重定向。

Dead Blending 是更新的惯性式过渡方案。Game Animation Sample 将它描述为支持 Blend Curve 的改进型 Inertialization，并用它平滑 Aim Offset 等会反复启停的姿势层。

两者解决的是“如何平滑切换”，不是“应该选择哪个动画”。Motion Matching、Chooser 或状态机负责选择目标，Inertialization / Dead Blending 负责让切换过程不出现明显 Pop。

## 与 ALS 的对应关系

| ALS 方案 | UE5 可引入的现代工具 | 关系 |
| --- | --- | --- |
| Velocity Blend、Movement Direction | Orientation Warping | 可以减少方向动画数量，但不一定完全替代方向权重 |
| Stride Blend + Play Rate | Stride Warping | 都用于速度匹配，应避免双重缩放 |
| Grounded Lean | Additive Lean / FBIK 身体响应 | Lean 仍可保留，FBIK 适合多目标约束 |
| Foot Trace + Foot Offset | Foot Placement | Foot Placement 可统一更多地面与骨盆逻辑 |
| Foot Lock | Foot Placement 的 Plant/Lock 行为 | 可迁移，但要避免两个系统同时锁脚 |
| Start / Stop / Pivot 状态 | Distance Matching | 可先局部替换停止、Pivot 和落地推进方式 |
| 大型移动状态机 | Motion Matching + Chooser | 属于架构级替换，数据准备成本最高 |
| Rotation Yaw Offset、转身补偿 | Orientation Warping、Steering、Offset Root Bone | 作用空间不同，需要按最终链路重新分工 |
| Dynamic Transition | Motion Matching 重新选姿、Chooser、过渡 Montage | 都用于释放不自然姿势，但触发方式不同 |

现代节点不是越多越好。每增加一层修正，都应明确它修改的是动画时间、局部骨骼、Root Motion、Mesh Root 还是 Actor Transform。

## 推荐的引入顺序

如果要把 ALS 风格系统逐步升级，不建议第一步就重写成 Motion Matching。

1. 先引入 Inertialization 或 Dead Blending，改善现有状态切换。
2. 用 Distance Matching 改造停止、Pivot 和落地等距离敏感动画。
3. 选择 Stride Warping 或现有 Stride Blend 作为主步幅方案，并重新标定 Play Rate。
4. 在方向动画覆盖不足时引入 Orientation Warping。
5. 独立验证 Foot Placement，再决定替换哪些 Foot IK、Foot Lock 和 Pelvis Offset 逻辑。
6. 对需要精确到达场景目标的 Montage 使用 Motion Warping。
7. 动画数据库和轨迹数据准备充分后，再评估 Motion Matching、Chooser 和 Blend Stack。

这种顺序能让每次改动只承担一个清晰职责，也更容易比较新旧方案的收益。

## 常见问题

### 多个节点同时修正同一件事

最常见的是同时启用 ALS Stride Blend 和 Stride Warping、同时运行旧 Foot Lock 和 Foot Placement，或者让 Motion Warping 与 Offset Root Bone 同时争夺 Root。结果通常不是效果更强，而是过度修正、抖动或姿势不可预测。

### 执行顺序不正确

一般应先产生或选择基础姿势，再做方向和步幅 Warping，最后做接触类 IK。若先把脚固定，再由后面的节点旋转根骨或改变步幅，脚部目标可能再次被破坏。

实际顺序仍取决于节点修改的空间和项目设计，应通过单独开关每层节点验证。

### 把 Root Motion、Mesh Root 和 Actor Transform 混为一谈

Orientation Warping 修改姿势方向，Offset Root Bone 修改 Mesh Root 相对胶囊的偏差，Motion Warping 修改 Montage Root Motion 到目标的轨迹，角色移动组件则控制 Actor 或胶囊。它们名称都带有方向、根或移动，但作用对象不同。

### 忽略插件和版本差异

这些能力分布在 Animation Warping、Animation Locomotion Library、Pose Search、Motion Warping、Control Rig 和 FullBodyIK 等插件中。部分节点在不同 UE5 小版本中更名、移动模块、调整输入，或者仍被标为 Experimental。

笔记记录的是现代 UE5 的功能分工，不是某一版本可以直接照抄的节点清单。正式实现前应固定目标引擎版本，再根据该版本文档和节点属性核对。

### 认为 Motion Matching 会自动修复所有动画问题

Motion Matching 只能从已有数据中选择更合适的姿势。数据库缺少对应动作、轨迹预测不准确、脚部接触数据错误时，它仍会得到不理想结果。Warping、IK、过渡和资产质量依然是系统的一部分。
